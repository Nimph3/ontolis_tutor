# OntoTutor 3.0 — свободный выбор начальной темы + DFS-обход веток

Локальное учебное веб-приложение на **FastAPI + Python + HTML/CSS/JavaScript**. Можно загружать разные предметные области в виде `.ont` или `.json` (JSON-экспорт ONTOLIS), выбирать доступную предметную область и понятия, **самостоятельно назначать начальную точку первым вопросом** и последовательно изучать выбранную ветку графа в глубину (DFS). После завершения ветки можно снова свободно выбирать понятие, не прерывая сессию.

## 1. Запуск на Windows

1. Установите **Python 3.10+**.
2. Распакуйте **весь архив**. Откройте папку `ontolis_tutor` в VS Code и терминал в ней.
3. (Рекомендуется) Создайте виртуальное окружение:

   ```powershell
   py -m venv .venv
   .venv\Scripts\activate
   #.\.venv\Scripts\Activate.ps1
   ```

4. Установите зависимости:

   ```powershell
   pip install -r requirements.txt
   ```

   В версии 2 появилась библиотека `python-multipart` — она нужна FastAPI для получения файла из формы `multipart/form-data`.

5. Запустите сервер:

   ```powershell
   uvicorn app:app --reload
   ```

6. Откройте **http://127.0.0.1:8000**. Документация API — **http://127.0.0.1:8000/docs**.

   На Linux/macOS активация окружения: `source .venv/bin/activate`.

## 2. Как загрузить другой `.ont` и начать обучение

1. В левой панели найдите **«Предметная область»**.
2. Нажмите **«＋ Загрузить .ont»** и выберите `.ont` или `.json` размером **до 5 МБ**.
3. Если файл корректен, он появится в выпадающем списке. Приложение автоматически переключится на него и выведет число понятий, связей и заполненных определений.
4. Если онтология использует нестандартные названия отношений, откройте **«Настроить типы связей»**. Выберите для них соответствующую **учебную роль** и нажмите **«Сохранить роли связей»**.
5. Отметьте понятия чекбоксами. Это **рамки доступных тем**, включая все их подтемы, а НЕ заранее заданный стартовый узел.
6. Укажите **минимум** засчитываемых вопросов и нажмите **«Начать обучение»**. Настройки блокируются.
7. Задайте **первый вопрос по любому понятию в выбранной области**, даже если это не корневой узел. Например, если отметили «Клетка», можно начать с «Митохондрия». Именно этот вопрос задаёт начальную точку.
8. Приложение строит DFS-обход **только из выбранного стартового узла** и последовательно предлагает оставшиеся узлы его ветки. Вопросы по другим узлам во время обхода не засчитываются. Вопрос по текущему понятию засчитывается и продвигает на следующий шаг.
9. Когда последний узел ветки изучен, приложение возвращается в режим **«выбор темы»**. Можно начать с любого другого понятия из выбранной области, включая ранее пройденное; число засчитанных вопросов не сбрасывается. Повторяйте, пока обучение нужно.
10. Обычное завершение станет доступно после установленного **минимального** числа принятых вопросов; даже после достижения порога можно продолжать обучение. Досрочное завершение доступно в любой момент.

**Важно о формате:** расширение `.ont` само по себе не гарантирует совместимость. Приложение принимает **текстовый JSON-экспорт ONTOLIS** с массивами `nodes` и `relations`. Сырые XML/OWL, RDF, ZIP и двоичные `.ont` не распознаются автоматически. Если файл другой структуры, понадобится конвертация или отдельный импортёр.

**Проверяемые ограничения файла:** до 5 МБ, 1–1000 понятий, до 5000 связей, уникальные ID, непустые названия понятий и ссылки связей только на существующие ID. Ошибку формата увидите рядом с кнопкой загрузки. Определения `attributes.def` могут быть не у всех узлов — программа покажет число незаполненных и честно скажет, что у соответствующего понятия определения нет.

**Можно попробовать без своего файла:** в архиве есть `examples/biology_demo.ont` — демонстрационная онтология по биологии (7 понятий и 6 связей). Загрузите её через интерфейс, раскройте настройки типов связей, назначьте `contains → has`, нажмите «Сохранить роли связей» и выберите понятие «Клетка». Получится маршрут «Клетка → Органоиды → Ядро → Митохондрия → Рибосома → Клеточная мембрана → Цитоплазма» — сначала углубляемся в ветку органоидов и только затем переходим к остальным компонентам.

## 3. Как трактуются отношения

В исходной онтологии связи уже названы понятными приложению словами:

| Учебная роль | Направление в исходных данных | Значение для обхода |
|---|---|---|
| `has` | целое → часть | Пройти от целого к части |
| `a_part_of` | часть → целое | Пройти в обратную сторону |
| `is_a` | частный класс → родительский класс | Пройти в обратную сторону |
| `is_instance` | экземпляр → класс | Пройти в обратную сторону |
| `used_for` | средство → назначение | Пройти от средства к цели |
| `use` | субъект → объект использования | Пройти к используемому объекту |
| `input` | ресурс → потребляющий узел | Пройти в обратную сторону, к входным данным |
| `output` | узел → результат | Пройти по направлению связи |
| `same_as` | понятие → синоним | Показывать связь, не создавать отдельный учебный шаг |
| `ignore` | любой | Не включать связь в маршрут |

Если у новой онтологии есть связь `contains`, которую автор использует в смысле «содержит», в интерфейсе следует выбрать для неё роль `has`. Тогда граф начнёт учитывать её при DFS **без изменения исходного `.ont`**. Обратная ситуация: ошибочно присвоенная роль может дать неправильный порядок — *смысл отношений необходимо определить по онтологии*, программа не может угадать его со стопроцентной точностью.

Настройки отношений каждой загрузки сохраняются отдельно в `data/ontologies/<id>/relation_mapping.json` и остаются после перезапуска. У исходного графа используется `data/relation_mapping.json`, если вы сохраняли его настройки. **Уже запущенные сессии сохраняют прежнюю версию графа**; новые роли влияют только на следующие сессии.

## 4. Как работает порядок обучения (версия 3.0)

**Почему изменили:** прежде после создания сессии сервер сразу вычислял `learning_path(selected_topics)`, и первый вопрос должен был относиться к первой теме маршрута. Пользователь не мог выбрать исходную точку.

**Теперь есть два режима одной сессии:**

1. **`choose_start` — свободный выбор.** Чекбоксы определяют допустимое множество узлов (отмеченные понятия и все их потомки по учебным рёбрам). Маршрута ещё нет. Первый распознанный вопрос выбирает узел внутри этого множества. Нельзя начинать с узла за пределами отмеченной области. Если узел не удалось определить, вопрос не засчитывается.
2. **`in_branch` — обязательный DFS.** Сервер создаёт `learning_path([начальный_узел])` и идёт в глубину: сначала одна дочерняя ветка полностью, затем следующая в пределах этой ветки. `visited` предотвращает повторы и циклы в рамках одного обхода. Для каждого шага требуется принятый вопрос о текущем понятии; вопросы по другим узлам возвращают `out_of_order` и не увеличивают счётчик.
3. **Завершение ветки.** После ответа по её последнему узлу режим снова становится `choose_start`: пользователь волен выбрать любую новую точку в разрешённой области, в том числе ранее изученную. В рамках новой ветки `visited` пересоздаётся — повторный выбор допустим.

**Пример:** в биологической онтологии выбрано понятие «Клетка» с подтемами. Если ученик сразу спрашивает «Что такое Органоиды?», DFS начнётся с органоидов и их внутренних тем, а не с «Клетки». Пройдя эту ветку, можно отдельно спросить «Что такое Клеточная мембрана?» или начать с самой клетки — это откроет новый маршрут.

**Минимальное число вопросов — не длина маршрута и не жёсткий максимум.** Достигнув минимума посреди ветки, ученик может нажать «Завершить» либо продолжить DFS. Когда ветка окончена раньше минимума, можно начать следующую. Принудительное завершение доступно всегда.

**Порядок одноуровневых подтем** не указан в исходном `.ont`. Для исходного графа мы оставили `data/curriculum_order.json` и резервные приоритеты в `graph.py`. У каждой новой онтологии создаётся **свой** пустой файл:

`data/ontologies/<id>/curriculum_order.json`

Пример содержимого для новой области:

```json
{
  "a": ["b", "c"]
}
```

Здесь `a` — ID родительского понятия, а `b`, `c` — ID его дочерних понятий в желаемом учебном порядке. Это влияет только на очередность **уже существующих по графу** дочерних связей, не создаёт новых связей. Остальные дети идут после них в порядке приоритета роли отношения и затем по ID. Редактирование этого файла выполняется **в текстовом редакторе**; после изменения **перезапустите сервер**. В веб-интерфейсе настройка ролей связей реализована, а ручная перестановка порядка дочерних узлов пока не реализована.

> Максимальное **настраиваемое минимальное** количество — 100 вопросов. Засчитанных вопросов может быть и больше, если пользователь добровольно продолжает после достижения порога.

## 5. Что изменилось в архитектуре

**Было в версии 1:** один объект `ontology`, загруженный при старте `app.py`; все сессии использовали именно его.

**Добавили в версии 2:** каталог `ontologies` хранит отдельные объекты `OntologyEntry`; каждый содержит ID, заголовок, путь и экземпляр `Ontology`. Объект `Session` хранит `ontology_id` и ссылку `graph` на граф, с которым сессия была создана. Это защищает уже идущее обучение от изменения выбора/настроек других пользователей. **В версии 3** объект `Session` дополнен `allowed_nodes`, `path`, `position`, `branch_number`, `branches_completed`. Отдельно хранятся общий счётчик `answered` и позиция в текущей ветке `position`. `path` пуст до первого распознанного вопроса.

| Файл | Зачем нужен |
|---|---|
| `app.py` | FastAPI, API загрузки, каталог онтологий и изолированные сессии |
| `graph.py` | Проверка структуры графа, индексы, сопоставление отношений, DFS, ответы |
| `data/ontology.ont` | Исходная онтология с определениями (не переписывается) |
| `examples/biology_demo.ont` | Пример второй предметной области для проверки загрузки и настроек отношений |
| `data/curriculum_order.json` | Учебный приоритет для исходной онтологии |
| `data/ontologies/<id>/ontology.ont` | Загруженный пользователем граф |
| `data/ontologies/<id>/meta.json` | Его имя для отображения в списке |
| `data/ontologies/<id>/relation_mapping.json` | Названия отношений → учебные роли |
| `data/ontologies/<id>/curriculum_order.json` | Независимый порядок дочерних понятий |
| `static/index.html` | Боковая панель выбора/загрузки и разметка чата |
| `static/styles.css` | Компактные карточки, большой чат, адаптивная верстка |
| `static/app.js` | Выбор графа, отправка файлов, блокировка, чат, восстановление сессии |

**Файлы загрузок не исчезают при перезапуске сервера.** Они лежат на локальном диске в `data/ontologies/` и автоматически перечитываются при старте. Но **сами сессии и история сообщений хранятся только в оперативной памяти**; при перезапуске сервера их восстановить невозможно. Браузер запоминает выбранную онтологию и ID последней сессии в `localStorage`, но это не резервное копирование диалога. Для постоянных сессий нужен отдельный слой хранения (например, SQLite).

## 6. REST API

| Метод и URL | Действие |
|---|---|
| `GET /api/ontologies` | Список загруженных графов и статистика |
| `POST /api/ontologies` | Загрузка файла через `multipart/form-data`, поле **`file`** |
| `GET /api/ontologies/{id}/relations` | Типы отношений и их учебные роли |
| `PUT /api/ontologies/{id}/relations` | Сохранить сопоставление ролей `{ "mapping": { "contains": "has" } }` |
| `GET /api/meta?ontology_id={id}` | Понятия и статистика выбранного графа |
| `POST /api/sessions` | Создать сессию по выбранной онтологии |
| `GET /api/sessions/{sid}` | Состояние учебной сессии |
| `POST /api/sessions/{sid}/ask` | Задать вопрос: выбрать начальную точку или продвинуться по текущему DFS |
| `POST /api/sessions/{sid}/complete` | Обычное завершение после минимального числа вопросов |
| `POST /api/sessions/{sid}/force` | Принудительное завершение |

Пример создания сессии на загруженной онтологии:

```json
{
  "ontology_id": "идентификатор-из-GET-api-ontologies",
  "selected_topics": ["a"],
  "question_count": 3
}
```

`ontology_id` необязателен для совместимости со старым вариантом API: по умолчанию выбирается `default`. Ответы читаются из `nodes[*].attributes.def`; если запрошены части/виды/связи, добавляются реальные соседние узлы и ID отношений. В `GET /api/sessions/{sid}` и в `state` ответа присутствует `mode: "choose_start" | "in_branch"`; `current: null` во время свободного выбора и объект текущего понятия при обходе; `course_length` — длина **текущей/последней** ветки. Результат `out_of_scope` означает, что начальный вопрос относится к неотмеченной области, а `out_of_order` — попытку перескочить на другой узел внутри DFS. Используется **правиловой поиск по названиям, а не LLM**: произвольная формулировка вопроса может быть не распознана. Начальная точка определяется только по явно названному понятию.

## 7. Ограничения и безопасность

- Это учебное **локальное** веб-приложение без аккаунтов, авторизации и ограничений для каждого пользователя. **Не выкладывайте сервер в открытый интернет** без защитного слоя, лимитов и контроля доступа к загрузкам.
- Поддерживается максимум 50 дополнительно загруженных онтологий в одной установке; файлы лежат на диске.
- Не все неизвестные типы связей автоматически интерпретируются: их надо назначить вручную в интерфейсе. Отсутствие связи или определения нельзя компенсировать программой без новых исходных данных.
- Одна связь может встречаться в нескольких местах графа; направление задаётся учебной ролью для **всех связей с этим названием** в пределах одной онтологии.
- Выбор нескольких сотен тем и подсчёт учебного маршрута рассчитаны на небольшой учебный граф, а не на промышленный граф знаний.

## 8. Проверки

Для запуска тестов:

```powershell
pip install pytest httpx
pytest -q
```

Тесты проверяют исходный граф, DFS, источники ответа, блокировку/завершение сессии, загрузку новой области, проверку некорректных файлов, сопоставление нестандартных отношений, независимость сессий, перечитывание загруженных онтологий с диска, **выбор начальной точки первым вопросом, запрет перескока, возврат к свободному выбору и продолжение после минимума**.
